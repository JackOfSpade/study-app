# Question design

## Role focus and tutor depth

The active role is a product engineer who owns consumer and creative web features end to end, with strong UI craft and appropriate working backend knowledge. `src/career-profile.ts` overlays 51 core Product Engineering objectives (`CORE_IDS`) at a maximum required depth of 3; it does not rewrite the 112-objective source bank or its original targets. Reference and optional objectives remain available as source material but are excluded from focused gates and automatic practice. The "Full original curriculum" setting reverses the overlay. Python interview fundamentals are unchanged.

Generation payloads carry the role's bounded scope guidance (`careerScopeGuidance`). Switching profiles never rerolls a question already issued.

New tutor exchanges allow at most one directly relevant prerequisite level (the tutor instruction in `scripts/lib/ai-contracts.mjs`). The probe parser still reads older saved observations with two levels (`SUB_FACET_DEPTH` in `src/knowledge-probe.ts`); new exchanges cannot create deeper branches. An unspecified gap outcome does not mark every unknown sibling as missing: only explicit findings are recorded, and unasked facets stay unassessed.

## Generation policy

Every question is written by Claude (`generate`). The instructions are assembled by `taskInstructions("generate")` in `scripts/lib/ai-contracts.mjs` from the constants in `scripts/lib/study-question-policy.mjs` and `scripts/lib/question-parts.mjs`; the request also carries `QUESTION_GENERATION_POLICY` from `src/ai.ts`. Each rule is sent once.

The top-level rule, shared by generation and tutoring, is **minimum evidence** (`MINIMUM_EVIDENCE_GUIDANCE`): ask for the smallest thing that proves the skill, once, as short as the skill allows. A second item, part, facet or follow-up is allowed only when it tests something the first does not. Extra probing is for after a miss. A complete correct answer ends the question or the part at once; where the reasoning is the skill, the question asks for the answer and its reason together.

The policy asks for:

- a standalone question: the shared prompt and the part on screen together supply the scenario, code, data, timing and rules needed to answer without the chat, and every rubric requirement is visible there;
- the smallest self-contained diagnostic, with one main problem and a follow-up only when it tests something the main problem does not, in plain language that never mentions the schedule, objective IDs, tiers or depth;
- depth 1 as code reading or reasoning, with an empty starter and no implementation requirement drawn from an objective's verb; at depth 3, for scoping and design objectives, only the brief and hard constraints are given and the learner states the assumptions;
- the contract and existing stable scope definitions copied exactly, with open knowledge gaps (`probeRecords`) as the apex of the question;
- interview realism: the problem shapes, constraints and follow-ups a working interviewer would use. For an objective about the learner's own projects, the learner picks a real project of their own and the rubric judges structure and honesty, never particular facts; a critique of a supplied answer is the exception and is limited to four one-line facts and one short answer;
- for the product-engineer profile, a consumer or creative web feature as the setting when the objective does not fix a domain (`careerScopeGuidance`);
- variety: the request carries up to five earlier questions on the same objectives (`earlierQuestions`: title, a 160-character opening and the asks, never answers or tutor text), and a regenerated question's `replaces` carries the replaced asks, so the new question changes scenario and the shape of its ask. Questions replaced earlier on the same question (`discardedQuestions` on the saved question, at most five) lead `earlierQuestions`, so a second regeneration does not return to the first discarded scenario.

`QUESTION_SHAPE_GUIDANCE` is the last block the generator reads: five numbered checks, run before returning, each rule stated once (the part mechanics live in `PARTS_GENERATION_GUIDANCE`, the minimum-evidence rule in `MINIMUM_EVIDENCE_GUIDANCE`). A fact a correct answer needs is never dropped; beyond that, the writer cuts:

1. Short reading: a few terse facts that a correct answer turns on (plus distractors when filtering is the skill), no story, cast or restated instructions, and no prompt line that previews or defines what the parts ask. Anything whose removal changes no answer goes.
2. One of each kind: one item of a kind and one of each different kind; a scope that lists several kinds does not oblige one per entry; no counts ("name two"); "identify each" or "list all" only when finding every instance is the skill, and then the list alone, never a second request per item ("giving for each", "why each"); no facet per list member.
3. One ask per part, in reasoning order: each part, read alone, is one request; a diagnosis comes before its remedy, and no part asks again for what an earlier part's reason already shows, restated, turned round (why the rejected option fails) or already guaranteed by an earlier answer. A self-audit ask is kept only when assessed, as the last part.
4. Answer check: the writer answers each part from the prompt and that part alone, checks that its words ask for what the rubric expects (a phrase with two readings names the one meant), that "exactly one" claims and traces are true to the facts, and that nothing gives the answer away: no definition of the tested term, label definitions in the words of the expected reasons, guideline, premise or qualifier on the ask stating the tested rule or criterion, category words for items, data listed in the expected answer's order, or an ask that rules an option out or names the kind of answer.
5. Rubric check: one judgement per line, checkable from the answer's words (never whether a figure sounds invented), no point credited or checked twice, and every claim a line requires true of the facts (code traced by the language's rules). Each element a line requires must be requested by its ask's own words (the writer quotes them, and cuts or names in the ask any element with none), and the line must accept every correct answer the facts support, checked against the shortest correct answer and one taking another route (another ground the facts give, another item fitting an open, plural or superlative ask); open asks use "such as" with complete correct examples that keep the ask's own constraints. A required reason answers the ask's "why" as literally read, never just a decision the prompt fixed; a line states each requirement once (no looser "also acceptable" alternative), and an allowance such as "nothing was measured" excuses only what it names.

## What the tutor accepts

The learner cannot see the rubric, so it is not the pass bar. The tutor's copy of the question carries the rubric lines as `problem.evidenceExamples` (`tutorProblem` in `src/ai.ts`), never as `rubric`, and `QUESTION_ADAPTATION_GUIDANCE` tells it to accept on the question or part on screen and the facet descriptions:

- an answer that is correct, makes no false or unsupported claim and contains every element the ask names is accepted, even where an example line words it differently or holds detail the ask does not request (a notation, a number format, both of two equivalent values, a caveat the ask does not call for);
- a value derived correctly from the given facts is a real value, and stating it loosely is a refinement unless the loose form claims more than the facts support;
- such a refinement is offered in at most one sentence while accepting, never as a reason to keep the question open;
- what the task needs is still required: a wrong result, a case whose absence makes the solution incorrect, a skipped element the ask names, or a claim the facts do not support is a miss;
- the tutor gives one reason for a miss and, when the learner shows that reason was wrong, says so and judges the answer again.

`TERMINAL_DIALOGUE_INSTRUCTION` states the test once more at the point of decision: keep the question open only for something false, unsupported or missing that can be named.

This came from a real question on 2026-11-19 whose rubric line required both completion rates and both measurement windows while the ask requested neither: the tutor held a truthful rewrite open over "increased by 7%" (61% to 68%), gave two different reasons for it, and delivered a credit-costing hint the learner had not asked for. The assessment still reads the full rubric, but judges each facet against what the question and its part asked: an element a rubric line requires that the ask never named (a remedy for a diagnosis, a specific figure, period, caveat or quality) is not required, so its absence never makes a facet unknown or assisted, while a false or unsupported claim still counts (`taskInstructions("assess")` in `scripts/lib/ai-contracts.mjs`).

`TUTOR_JUDGEMENT_GUIDANCE` (in `scripts/lib/study-question-policy.mjs`), sent with both the open-question and the after-completion instruction, carries the same idea into the argument that follows:

- the example lines are one route to a full answer; any correct, sound argument that answers the ask is accepted, and the tutor never steers back to an example's wording or calls an example's point the "real" reason once the learner's argument already answers the question;
- a point that only explains another accepted point (for example why two costs come out equal) is not an extra requirement;
- a challenge is weighed on its merits: a concession, once made, holds in every later reply, and a wrong objection gets the specific fact or step that fails;
- a supporting fact the learner says they do not know, and no facet assesses (a definition, or the cost of a standard operation), is stated in one line as clarification; while the question is open, a fact a facet assesses still goes up the hint ladder;
- "one question at a time" means one question per reply, and internal field names such as `review.openGaps` never appear in text.

After completion the tutor says the saved result is final only when the learner asks to change, reopen or re-grade it, or whether the discussion changes it, not as a footer on every reply.

This came from a real question on 2026-11-20 (heap versus one sort for an end-of-day report). The learner's final answer, equal O(n log n) cost so the simpler sort wins, was sound, yet the tutor kept naming the rubric's "no interleaved arrivals" as the deciding reason after conceding that unused capability was not a reason. It also never said that building a heap is O(n) when the learner twice said they did not know, and it ended every post-completion reply with the same finality line, once quoting `review.openGaps`.

`node --import tsx scripts/ai-capture/build-acceptance-cases.ts --out <file>` builds nine tutor cases for this rule, with no network use: one question whose rubric line is deliberately more specific than its ask, and one learner answer each. A case id starts with the verdict written down beforehand, `accept-` or `open-`; the `open-` cases (an unmeasured figure, an unhedged cause, a teammate's work claimed, a solution that ignores a named requirement) guard against over-leniency. Replay them with `npm run ai:ladder -- run --cases <file> --settings sonnet:low --reps 3 --name <name>`, which prints where it wrote `results.jsonl`; then `node --import tsx scripts/ai-capture/build-acceptance-cases.ts --score <results.jsonl>` prints how many replies per case gave the expected verdict. Results are in [AI model and effort selection](AI_MODEL_SELECTION.md).

The tutor and the assessor follow the same rule: one general statement, or the point worked for one item, establishes facets of the same kind; a correct answer is not kept open for elaboration; and a short correct answer is never marked down.

`estimatedSolveSeconds` is the time a learner who already has the skill needs for one complete correct answer to the whole question, and `partSolveSeconds` the same estimate for each part. Nothing in the app reads them except validation and the capture metrics.

A correct answer to one question is practice evidence, never certification of full objective mastery. Previously captured questions, conversations and retries keep their stored text.

## One part at a time

A question that asks for more than one thing is shown one ask at a time, so the learner starts with a single thing to answer. `generate` returns the shared material (scenario, code, data, fixed facts) as `prompt` and each ask as an entry of `parts` (one or more, one per thing asked for. The count has no limit: a limit of three, removed on 2026-11-19, pushed the writer to pack several asks into one part; each part's solve time bounds it instead, see Question length). A part that holds two requests (two questions, a question and an instruction, or "do the same for") is sent back for the one correction with the reason (`compoundPartProblem` in `scripts/lib/question-parts.mjs`); the check reads prose, so it is waived on the last attempt and never refuses a question. The app stores the whole text in `problem.prompt`, which every other reader uses (assessment, history, bug reports), and, when there are two or more asks, the staged form in `problem.staged: { shared, parts }`. A question with one ask is shown whole, as is any question saved before 2026-11-18.

While a staged question is open the question pane shows the shared material and the open part only. Each tutor request carries `stage: { part, of, question }`; the tutor works on that part alone and never mentions a later one. When the part is answered, or the learner gives up what remains of it, the tutor returns `partComplete: true` with `complete: false`. The app records that message in `encounter.partReady` and the conversation ends with a "Next part" button, shown only then. The part stays open until the learner presses it, so they can read the confirmation and ask more about that part first (those requests carry `stage.confirmed: true`). Pressing it records the last message of the part in `encounter.partsDone`, fades the old part out and writes the next in its place, with the finished parts under a closed "Earlier parts" disclosure. The conversation stays on screen, with a marker after the last message of each finished part (until 2026-11-19 it was cleared when a part opened). Every tutor request carries the whole conversation; `stage.since` is the seq of the last message before the open part, so the tutor reads later messages as answers to that part even when the learner does not restate it. A facet given up when leaving a part is recorded as a knowledge gap at once. Only the last part can finish the question: the relay and the app both reject `complete: true` while a part is still hidden. It stays one question, with one conversation, one completion and one assessment. A finished question shows every part.

The rules live in `scripts/lib/question-parts.mjs` (guidance text and validators) and `src/question-parts.ts` (what is shown).

## Question length

A question has no total time limit; each part does. Until 2026-11-27 every question had to fit one sitting of 15 minutes (`estimatedSolveSeconds` at most 900). That cap kept out the problems real interviews use, and the learner's actual cost of a long question was a wrong turn found only at the end. Now a learner moves on only after the tutor confirms the open part, so a part's length is what a wrong turn can cost, and that is what is bounded, at ten minutes (the user's decision, 2026-11-27; five minutes was tried first the same day and raised to ten at the user's request).

- `generate` returns `estimatedSolveSeconds` (at least 30, no upper limit) and `partSolveSeconds`, one estimate per part in order, each positive and at most 600, ten minutes (`PART_SOLVE_SECONDS_MAX` in `scripts/lib/question-parts.mjs`). A reply with a part over the limit, or with the list missing or miscounted, is sent back for the one correction with the instruction to cut what the skill does not need and split the rest into steps (`partSizeProblem`); when a part also asks for two things, both reasons go in that one correction. A short part is never sent back. The estimates are the writer's own, so like the one-ask check this is waived on the last attempt and never refuses a question; the app keeps a well-formed list and drops any other.
- A problem whose full solution takes longer than one part (an interview coding problem, an implementation, a design, a multi-step derivation or debugging session) is kept whole when the objective calls for it and cut into the consecutive steps a strong candidate would take, each a checkpoint that can be judged alone (`PARTS_GENERATION_GUIDANCE`). Implementation is no exception: a long one is built over several parts, one function, method or distinct piece of behaviour per part (cases of one kind stay together), added to the same code, and each is confirmed before the next opens. The learner's earlier code stays in their workspace and the conversation.
- A later part that needs an earlier step's result (a value, a data shape, a fixed decision the question made, or the interface and behaviour of code written earlier, never that code) states it in one short line before its ask. Where the earlier step was the learner's own choice, the later part says to continue with the approach they chose, never names one, and works for any reasonable choice. When the learner gives up such a step, the tutor's closing reply names one reasonable choice (or the result) to continue from (`PARTS_TUTOR_GUIDANCE`); the gap is recorded either way. The earlier part is finished by then, so this gives nothing away, and a learner who gave that step up still continues from the right state. The assessment reads such a line as context for the later part, never as help for the earlier answer (`ASSESSMENT_HELP_GUIDANCE`).
- Parts run in the order the reasoning runs, and a later part tests only what a complete answer to the earlier parts, including any reason they ask for, does not already show (`QUESTION_SHAPE_GUIDANCE`, check 3). This came from a real question on 2026-11-28 about a crop preview that never updated: part 1 asked which kind of test would have caught the bug and why, and part 2 asked why the two existing tests passed, part 1's reason asked again in the wrong order. A regenerated question then asked whether a regression test "would have failed before the release" that introduced the bug, where the point was after it, which led to the answer check (check 4).
- The 2026-11-28 generate quality loop (five rounds; 2, 5, 6, 6 and 6 of 12 real questions passed a reviewer's check) kept finding two faults: rubric lines requiring elements the ask never named or accepting one of several correct answers, and prompts or asks giving the answer away. Each round appended special cases; on 2026-11-28 they were merged into the general rules of checks 4 and 5 (quote the ask, a second correct route, the give-away list), bringing the block from about 1,600 words back under 1,000. Three validators back the prose, each sent back for one correction and waived on the last attempt (`scripts/lib/question-parts.mjs`): `compoundPartProblem` also flags a part that repeats a request over a list ("for each,", "label each", but not "for each user" in a specification), asks for a count of one kind ("name the two assumptions") or lists several asks in one sentence ("describe it: what ..., which ... and why", but not one answer with its reason); `promptPreviewProblem` flags a prompt that says what the learner will be asked ("you'll restate", "your task is to"); `rubricLooseningProblem` flags a rubric line that requires a point and then accepts less ("must make the point ... Saying only that ... is also acceptable"), but not a second correct route ("returning the promise is also accepted"). Round 1 of the 2026-11-27 loop (5 of 12 passed) found lines requiring what good practice or another part wanted rather than the ask (a page-size parameter, `type="button"`, the cause of work when the ask was why it is unnecessary), later parts crediting an earlier reason turned round, and an ask stating the tested criterion; checks 3 to 5 were sharpened in place, keeping the block at 1,000 words. Round 2 (1 of 12 passed) showed the same root: the rubric was written from the writer's one intended answer while the ask allowed others (a second ground for the "why", a second item for "least loss" or "what problem", a second reading of "the request was met"), plus "for each" requests the old check-2 wording allowed, a search listing in call order, a factually wrong required reason and a line judging whether a figure "sounds invented". Checks 2, 4 and 5 were reworded in place (987 words), and `compoundPartProblem` now also flags "For each type, state", "giving for each", "why each" and an open plural ask ("which problems"), and no longer flags a lead-in clause ("Knowing what you know now, what ...").
- The tutor accepts a part only when it is answered correctly (`PARTS_TUTOR_GUIDANCE`). A learner who says they do not know the rest of a part, or wants to move on, can still leave it: what they gave up is recorded as a knowledge gap, and the next part's opening line supplies the result it needs.
- Minimum evidence still holds: a smaller problem that proves the skill is better, and a long estimate earns nothing. What changed is that a problem the objective needs is no longer cut down to fit 15 minutes.

Evidence on sitting length (researched 2026-11-11): there is no real 10 to 15 minute attention cliff (Wilson and Korn 2007; Bradbury 2016), but fixed study/break cycles beat self-regulated long stretches on fatigue and concentration (Biwer et al. 2023, Br J Educ Psychol). Each confirmed part is a natural place to stop: the open part and the conversation are saved and survive a reload.

Older saves may hold a `segments` plan on a question and a `thread` on the record or a conversation, from a split-question design that was never wired into the study workspace. Those fields are carried through as saved data and nothing reads them; such a question is worked as a whole.

## Rejected replies

A reply the gateway's validator rejects gets one correction, which shows the model its own rejected reply (the first 6,000 characters) with the reason. A reply the gateway accepted but the app refuses (`validateProblem` or the scope checks) is retried under a new request identity, because the gateway keeps accepted answers by request id for ten minutes and would otherwise hand back the same reply. A transport failure still retries the exact saved request.

## Measuring questions

`node scripts/ai-capture/question-metrics.mjs <results.jsonl>` prints, with no network use, the reading load of generated questions in a ladder results file: words and bullet lines outside code, part count, the share of text shown up front, facet count, the estimated solve time of the whole question (`estimatedSolveSeconds`) and of its longest part (`partSolveSecondsMax`, which should stay at most 600), the longest rubric line in words (`rubricLineWordsMax`: a long line usually joins several requirements, and each one the ask does not name is a requirement the learner cannot see), and whether a part asks for a per-item justification. No text metric can tell whether a rubric line asks for more than its ask does; the acceptance cases above test that on the tutor's side. There is no hard length limit: code-reading questions are legitimately long, so length is reported, not rejected.

## Limits

- The generated bank is not adaptive beyond the scheduler's contract and the recorded probe gaps; a prompt cannot rewrite scheduler state, version or evidence constraints.
- Question quality has been judged on synthetic cases only; see [AI model and effort selection](AI_MODEL_SELECTION.md).
